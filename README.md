# Microcontroller-Lab04: A Cooperative Scheduler

## Course Information

**Course:** Microprocessors-Microcontrollers (CO3009)  
**Laboratory:** Lab 04 – A Cooperative Scheduler

## Overview

This repository contains the STM32CubeIDE and Proteus projects for Lab 04.

The laboratory focuses on implementing a **cooperative task scheduler** on the **STM32F103C6**. A periodic TIM2 interrupt updates task timing, while the main loop executes ready tasks. This separates timekeeping from application code without using blocking delays to schedule tasks.

The demonstration uses five LEDs with different execution periods, a 10 ms timestamp callback, and a one-shot checkpoint. Messages are sent through USART2 to the Proteus Virtual Terminal.

## Objectives

- Implement a scheduler with initialization, task registration, periodic updates, dispatching, and task deletion.
- Configure TIM2 to generate a regular **10 ms tick**.
- Run five independent LED tasks at **500, 1000, 1500, 2000, and 2500 ms** intervals.
- Schedule multiple callbacks concurrently, with different initial delays.
- Report elapsed time through `get_time()` at 10 ms resolution.
- Demonstrate both periodic and one-shot tasks.

## Scheduler Implementation

The scheduler is implemented in `STM32/Core/Src/scheduler.c`, with declarations in `STM32/Core/Inc/scheduler.h`.

| Function | Purpose |
|---|---|
| `SCH_Init()` | Clears the task table before registration. |
| `SCH_Add_Task()` | Registers a callback with an initial delay and period, specified in milliseconds. |
| `SCH_Update()` | Called by the TIM2 interrupt to update task delays and mark due tasks. |
| `SCH_Dispatch_Tasks()` | Executes ready callbacks from the main super-loop. |
| `SCH_Delete_Task()` | Removes a task; used when a one-shot callback finishes. |

The current implementation stores up to **40 tasks** in an array. Each record contains a function pointer, delay, period, pending execution count, usage flag, and task ID.

## Timer Configuration

The application uses an **8 MHz timer clock** with the following TIM2 settings:

| Parameter | Value |
|---|---|
| Timer | `TIM2` |
| Prescaler | `7999` |
| Auto-reload period | `9` |
| Interrupt frequency | `100 Hz` |
| Interrupt interval | `10 ms` |

The tick interval is calculated as:

```text
T_tick = (7999 + 1) × (9 + 1) / 8,000,000 = 0.01 s = 10 ms
```

The timer callback increments the system tick counter and invokes `SCH_Update()`. `get_time()` converts the tick count into elapsed milliseconds.

## Scheduled Tasks

The application registers all tasks **before starting TIM2**.

| Callback | Initial delay | Period | Action |
|---|---:|---:|---|
| `red()` | 0 ms | 500 ms | Toggle red LED |
| `yellow()` | 100 ms | 1000 ms | Toggle yellow LED |
| `green()` | 200 ms | 1500 ms | Toggle green LED |
| `blue()` | 300 ms | 2000 ms | Toggle blue LED |
| `aqua()` | 400 ms | 2500 ms | Toggle aqua LED |
| `print_time_10ms()` | 0 ms | 10 ms | Print `get_time()` over UART |
| `my_checkpoint()` | 3000 ms | Once | Print a checkpoint message |

The five LEDs are connected to **PA5–PA9**. **USART2 TX/RX** uses **PA2/PA3**, with serial output configured at **115200 baud**.

## Running the Simulation

1. Import `STM32/` into STM32CubeIDE and build the project.
2. Open `Proteus/LAB_4.pdsprj` in Proteus.
3. If necessary, configure the STM32 component to use the firmware generated by STM32CubeIDE.
4. Start the Proteus simulation and open the Virtual Terminal.
5. Observe the five LED toggles, millisecond timestamps, and the one-shot checkpoint message.

The expected timestamp increments are approximately **10 ms**. Actual callback execution can be delayed by other tasks and blocking UART transmissions.

## Implementation Notes

This repository reflects the current source code. `SCH_Add_Task()` and `SCH_Delete_Task()` currently return `void`, although the lab handout specifies an ID and status return value. `SCH_Update()` also scans the task array on each interrupt. These are areas for improvement against the stated laboratory requirements.
